ADR uses four decorators to wire behavior onto your classes. Three live on the `Operator`
(`@observe`, `@goals`, `@act`); one lives on the `Policy` (`@decide`, covered in
[Policies](/concepts/policies)). All are registered **once at class-definition time** via
`__init_subclass__` — no per-instance setup.

## `@observe` — mandatory

Receives the cycle's `Snapshot`, returns a plain `dict`. Called every cycle, before DECIDE.

```python
@observe
def extract(self, snapshot) -> dict:
    results = [v for k, v in snapshot.observations.items()
               if k.startswith("result.") and isinstance(v, dict)]
    return {"radius": snapshot.objectives.get("radius", self.radius),
            "results": results}
```

`@observe` is the **single assembly point for all metrics** — task results from
`snapshot.observations`, operator state from `snapshot.objectives`, or any external source (a
telemetry subscription you update in `main()`). Goals read *exclusively* from the dict it returns.

<Note>
If `@observe` is missing, `run()` raises `TypeError` before the first cycle. There is no default
observation — an operator is domain-specific by definition.
</Note>

You can also read past cycles inside `@observe` via `self.cycle_history` (previous completed
snapshots, oldest first, up to 64) — useful for detecting stagnation:

```python
@observe
def extract(self, snapshot) -> dict:
    radii = [s.objectives.get("radius") for s in self.cycle_history[-5:]]
    stale = len(set(radii)) == 1 and len(radii) == 5
    return {..., "stagnating": stale}
```

## `@goals` — optional

Returns a `Goal` or `list[Goal]`. These **static goals** are evaluated alongside any runtime goals
every cycle. See [Goals](/concepts/goals).

```python
@goals
def convergence_criteria(self):
    return Goal(name="converged", metric="radius",
                threshold=0.005, direction="minimize")
```

## `@act` — a capability

Marks an async method as something the operator can do. The method **runs in the operator's event
loop with `self` available**. Its return type decides the execution mode:

| Return type | Execution mode |
|-------------|----------------|
| `asyncio.Future` | Async — tracked via done-callback; result arrives next cycle |
| Plain value (`dict`, …) | Local — delivered to the inbox via `put_nowait`, visible next cycle |
| `None` | No-op — the method ran but produced no trackable result |

<CodeGroup>
```python Local
@act
async def evaluate(self, x: float, seed: int = 0) -> dict:
    rng = random.Random(seed)
    return {"x": x, "value": (x - TARGET) ** 2 + rng.gauss(0, 0.03)}
```

```python Backend task
@act
async def dock(self, candidate: str) -> dict:
    return self.engine.function_task(_dock_impl)(candidate=candidate)
```

```python Orchestration block
@act
async def md_refine(self, candidate: str):
    async def _block(c: str) -> dict:
        prepped = await self.engine.function_task(_prep)(c)
        return await self.engine.function_task(_simulate)(prepped)
    return self.engine.block(_block)(candidate)
```
</CodeGroup>

### `@act` methods vs module-level impls

The `@act` method is the **dispatch point**; the actual computation lives in a separate
**module-level async function** (`_dock_impl`, `_prep`, …). Those impls are pure and testable, take
no `self`, and — crucially — must be importable (picklable) under `ProcessPoolExecutor`.

<Note>
**Module-level impls must not take `self`.** They are dispatched to a backend executor; only the
kwargs you pass reach them. Anything needing `self` (e.g. `self.engine`) belongs in the `@act`
method body. With `ThreadPoolExecutor` or local execution any async function works; with
`ProcessPoolExecutor` it must be module-level. See [AsyncFlow integration](/integrations/asyncflow).
</Note>

### Dependencies between acts

An `@act` that needs upstream results accepts `*dep_futures` as positional args. The runtime
resolves an action's `depends_on` UIDs to live futures and passes them through — the policy never
handles a `Future`. See [Decisions & Actions](/concepts/decisions-and-actions).
