---
title: "Resource-Aware Steering"
description: "One Goal type for science and hardware — throttle on CPU, memory, or queue depth."
---

ADR is built for HPC, where "is the science done?" is only half the question — the other half is "is
the cluster healthy and am I under budget?" Both are expressed with the **same** `Goal` type, because
`Goal` is source-agnostic: it only cares what `@observe` puts into the obs dict.

**Runnable example:** [`examples/10-resource-aware-search.py`](https://github.com/radical-cybertools/radical.adr/blob/main/examples/10-resource-aware-search.py)

## The core idea

A scientific convergence goal and a resource constraint sit side by side:

```python
@goals
def criteria(self):
    return [
        Goal(name="converged", metric="radius", threshold=MIN_RADIUS, direction="minimize"),
        Goal(name="cpu_healthy", metric="cpu_percent", threshold=CPU_LIMIT, direction="minimize"),
    ]
```

ADR has no telemetry classes and no special resource API. `cpu_percent` is just another key the
policy and goals read from `obs`.

## Surfacing resource metrics in @observe

`@observe` is the single assembly point. It can pull `cpu_percent` from a user-managed telemetry
subscription you update in `main()`, completely outside ADR:

```python
@observe
def extract(self, snapshot) -> dict:
    results = [v for k, v in snapshot.observations.items() if k.startswith("result.")]
    return {
        "radius": snapshot.objectives.get("radius", 5.0),
        "results": results,
        "cpu_percent": self.telemetry.cpu_percent,   # external source, your code owns it
    }
```

<Note>
**`snapshot.runtime` is never checked by goals automatically.** Any resource or telemetry metric
must be surfaced explicitly through `@observe`, or the goal that reads it returns `False` and warns
once. This is deliberate — ADR steers on what you choose to observe, nothing hidden.
</Note>

## Throttling, not just stopping

A goal stops the operator; the *policy* reacts mid-flight. A resource-aware policy throttles the
number of tasks it spawns when pressure is high:

```python
@decide
async def run(self, obs):
    budget = 1 if obs["cpu_percent"] > 80 else 4     # back off under load
    return Decision(actions=[
        self._act.evaluate(x=...) for _ in range(budget)
    ])
```

Same operator, same goals — the steering changes with the metric.

## Two metric sources, identical code

The example ships with a `--local` mode that simulates `cpu_percent` via `update_param` instead of a
real backend subscription. The operator code, the goals, and the policy are **identical** — only the
metric's origin differs. That is the source-agnostic property in action:

```bash
python examples/10-resource-aware-search.py           # real ConcurrentExecutionBackend
python examples/10-resource-aware-search.py --local   # simulated CPU, no RHAPSODY
```

## Throttle on in-flight load with `inflight`

Resource pressure isn't only external — you may want to cap how much work *this operator* has in
flight. The read-only `Operator.inflight` property (count of `PENDING` + `RUNNING` tasks) is built in;
surface it through `@observe` and let the policy throttle:

```python
@observe
def extract(self, snapshot) -> dict:
    return {..., "inflight": self.inflight}

@decide
async def run(self, obs):
    budget = max(0, 8 - obs["inflight"])      # keep ≤ 8 tasks in flight
    return Decision(actions=[self._act.evaluate(x=p) for p in points[:budget]])
```

ADR never drops spawns on its own — throttling is always the policy's choice, so dynamicity is
preserved. You can also target `inflight` with a `Goal` (e.g. stop draining once it hits 0).

## A hard cap that can't be blocked: `Budget`

A `Goal` throttles or signals convergence — but a **compute/resource ceiling that must stop the run no
matter what** is a different thing, and it should not be a goal. ADR AND-combines the static goal with
any runtime goals, so a budget expressed as a goal can be blocked forever by an unsatisfiable
(possibly agent-added) goal and never fire. Use `Budget`:

```python
from radical.adr import Budget

op = SearchOperator(
    engine,
    budget=[Budget("trials", 50), Budget("usd_cost", 20.0)],   # hard stops
)
```

A `Budget(metric, limit, direction="max")` is checked every cycle **outside** goal checking (reading
the metric from `obs`, then `snapshot.objectives`), so no goal composition can keep the run alive past
its cap. `"max"` stops when `value >= limit`; `"min"` when `value <= limit`.

<Note>
**Goal vs Budget.** A `Goal` is part of *what convergence means* — a run stops when all goals are
satisfied, and a policy can throttle on the same metric mid-flight. A `Budget` is *when to give up
regardless* — an independent termination guarantee that goal state cannot block. Use a `Goal` to
express "healthy enough to keep going"; use a `Budget` for the hard trial/token/dollar/second ceiling.
See [api-boundary](/reference/api-boundary).
</Note>

## Beyond CPU

The same `@observe` pattern tracks GPU utilization, memory pressure, or queue depth as `Goal` metrics,
and any spend counter (trials, tokens, dollars, seconds) as a `Budget`. See the three-goal "hits AND
budget AND cpu" pattern in
[Goals & convergence](/guides/goals-and-convergence#multiple-static-goals-and).
